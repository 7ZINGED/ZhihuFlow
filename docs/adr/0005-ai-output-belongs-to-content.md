# ADR-0005：AI 产物归属于内容，不归属于收藏夹成员

- 状态：已采纳
- 日期：2026-11-24
- 相关：ADR-0004（队列真相源）、ticket 12（成员继承来源）、ticket 13（本决策）

## 背景

`id = ${collectionId}_${contentId}`，一行代表一条「收藏夹成员关系」（见 GLOSSARY）。同一篇回答被收进「技术」和「待读」是常见用法，于是本地会有两行。

`handleBatchAI` 按行筛选目标，`queueEngine` 按 `articleId` 推进，两者都不知道两行是同一篇内容。结果：

- 同一次批次里，同一篇内容被分析两遍，付两遍费用；
- 两行各自拿到一份 AI 结论，摘要、标签可能不一致，用户看到「同一篇有两个答案」；
- 精读模式代价最高，重复成本最明显。

ticket 13 列出了三个候选（构建期折叠 / 写回期传播 / 接受重复）。实现前的核对否定了「三选一」的前提。

## 决策

**1. 队列构建时按 `contentId` 折叠。**

`handleBatchAI` 在「跳过已处理」的交互确认之后，对最终待处理集合折叠，同一内容只派一个代表任务。代表优先取「尚未完成当前模式」的成员（复用 `isModeCompleted`，字段映射与 ADR-0004 一致）；全部已完成时取选择顺序中的第一行。

**2. 写回时向同 `contentId` 的其他成员补空，不覆盖。**

新增 `applyAIResult(articleId, patch)`：直接目标行整体写入；同内容的其他行只接收自己仍然为空的字段。空值判定：`undefined` / `null` / 空字符串 / 空数组；`false` 与 `0` 是有效值，不算空。

**3. 执行器不认识成员关系。**

`queueEngine` 不改。折叠发生在构建队列之前，因此一个分片里不会出现同一内容的两行；引擎仍然只认 `articleId`。

## 理由

- **折叠必须发生在构建期，而不是执行期。** 执行期折叠要在引擎里维护 `contentId → 代表行` 的运行态映射，并额外处理分片内的重复、失败后是否重试、断点恢复后的映射重建。这些复杂度换来的收益，构建期一行过滤就能拿到。
- **传播必须发生在仓储层，而不是引擎端口。** 三个单篇分支（粗读 / 分类 / 精读）都直接 `db.articles.update`，只有分类批处理走 `updateArticle` 端口。放在端口上就要在四处各写一遍，且新增 AI 入口时容易漏。
- **补空而不是覆盖。** 与 `mergeArticle` 同一原则：绝不静默覆盖本地已有产物。用户手工改过的标签、手工调过的分拣评级没有「人工」标记，任何覆盖规则都会把它们一起冲掉；补空的最坏后果是陈旧，用户对这一行显式重跑即可修复，而覆盖的后果是不可逆的意图丢失。
- **队列任务数应当等于真实 AI 调用数。** 折叠让用户在按下按钮前看到的篇数就是费用，比在执行期偷偷跳过更诚实。

## 后果

- 同一内容在一次批次里只付一次费用；被折叠掉的成员在代表行写回后立即补齐，不会停留在「未处理」。
- 用户选择「全部重跑」时不做折叠——显式要求重跑就意味着接受 N 次调用，此时折叠会让「我选了三篇只变了一篇」难以解释。
- 重跑某一行只刷新那一行；同内容其他已有结果的成员保持原样。这是补空规则的直接后果，也是有意为之。
- 功能上线前已经存在的重复行，会在任一同内容成员下次被分析时补齐。队列里已经存在的重复任务不会被自动删除，随自然消化退出。
- 未做：按 `contentId` 折叠的「历史库存清理」。它属于一次性数据修复，不是调度规则，若需要另开票。

## 被否决的方案

| 方案 | 否决原因 |
| :--- | :--- |
| 只在执行期按 `contentId` 跳过已完成的兄弟行 | 要在引擎里维护运行态映射、处理分片内重复与断点恢复重建；且队列显示的篇数与实际调用数脱节 |
| 每次 AI 写入都覆盖同内容所有成员 | 会静默冲掉用户对某一成员的手工标签与分拣评级，且无法区分「AI 旧结论」与「人工修改」 |
| 接受重复，不写代码 | 同一篇两条不同摘要会被当成 bug 报告；精读的重复成本足以让用户放弃批量功能 |
