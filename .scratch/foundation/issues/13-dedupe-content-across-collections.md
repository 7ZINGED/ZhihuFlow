# 13: 同一内容的多条收藏夹成员会被各分析一次

**What to build:** 决定并实现「同一 `contentId` 在多个收藏夹各占一行」时，AI 阶段如何处理，避免为完全相同的内容付两遍费用、并让成员之间的产物保持一致。

**Blocked by:** 12（已定性）、07（已完成）

**Status:** ready-for-human

- [ ] 在三个方案中拍板（见下）
- [ ] 若选「分析去重」：队列构建或引擎入口按 `contentId` 折叠，只保留一个代表行，结果写回时同步到同内容的其他成员
- [ ] 若选「结果传播」：任一行分析完成后，把 AI 产物复制到同 `contentId` 的其他行（需要一条按 `contentId` 更新的仓储方法）
- [ ] 若选「接受重复」：在 `GLOSSARY.md` 与设置面板写明成本后果，不写代码
- [ ] 回归测试：同一 `contentId` 两行时，AI 调用次数符合所选方案

## 三个方案

| 方案 | 成本 | 一致性 | 风险 |
| :--- | :--- | :--- | :--- |
| A. 队列按 contentId 去重 | 只付一次 | 代表行有新结果，其他行需同步写入 | 取消勾选/选择逻辑要按内容而非按成员 |
| B. 任一行完成后传播 | 只付一次 | 最好 | 需要按 `contentId` 批量更新，写放大；用户对某成员的单独修改会被覆盖 |
| C. 接受重复 | 付 N 次 | 最差（各成员摘要可能不同） | 无代码风险，但用户可能困惑「为什么同一篇有两份不同摘要」 |

## Comments

- 2026-11-24: 现状：`handleBatchAI` 的目标筛选按行（成员）进行，`queueEngine` 也按 `articleId` 推进，没有任何按 `contentId` 的折叠或传播。
- 2026-11-24: 触发条件不算罕见——同一篇高赞回答被收进「技术」和「待读」两个收藏夹，是常见用法。
- 2026-11-24: 建议倾向 A：与「成员关系」模型一致（一行仍是一条成员），只是在调度层折叠；B 的写放大会让用户的手工修改被静默覆盖。
